# 通用开发规范

## 适用范围

本规范适用于整个仓库。约束优先级依次为：用户明确要求、根目录及最近目录的 `AGENTS.md`、当前
OpenSpec change、`docs/spec` 中的适用规范、目标模块的现有模式。发现冲突时先明确事实并统一规则，再继续实现。

## 基础约束

- 使用根 `package.json` 要求的 Node.js 和 pnpm，不使用 npm 或 Yarn 改写 lockfile。
- 内部依赖使用 `workspace:*`，外部依赖使用根 `pnpm-workspace.yaml` 的 `catalog:`。
- 应用可以依赖共享包；共享包不得反向依赖 `apps/*`，也不得跨包 deep import。
- TypeScript 保持严格类型；Python 遵循 API 现有 Ruff 和 Django 约定。
- 命名、错误处理、日志、状态管理和组件实现优先沿用相邻代码模式。
- 在系统边界验证外部输入；权限校验必须在服务端执行。
- 不把密码、Token、Cookie、用户内容或个人信息写入代码、日志和跟踪文件。

## 变更原则

1. 使用 OpenSpec 明确目标、非目标、受影响模块和可观察验收场景。
2. 只有存在重要技术取舍、跨模块契约、数据迁移或回滚问题时，才需要详细 design。
3. 保持改动聚焦，不混入无关重构、全库格式化或无必要的依赖升级。
4. 自动化测试不作为默认任务；只有用户明确要求时才新增或运行，不固定执行完整仓库检查和构建。
5. 对用户、开发者或环境行为有影响时同步更新文档。
6. 团队定制优先放在现有配置、扩展点或清晰的独立模块中，降低后续同步上游的成本。

## 兼容与上游维护

- 不重写已经共享的上游历史；上游同步通过独立变更完成并记录 upstream SHA。
- 公共 API、事件、环境变量和数据库 schema 的破坏性变化必须说明兼容、迁移和回滚边界。
- 保留 Plane 的版权和 SPDX 声明，并遵守 AGPL-3.0-only 的源码提供要求。

## 完成定义

变更完成需满足：

- 实现符合 OpenSpec 场景和适用模块规范。
- 运行时实现完成后，主 Agent 已通过 `scripts/test/deploy-test.ps1` 部署受影响服务；本地主机工具缺失不作为部署阻塞。
- 主 Agent 已创建一个未参与实现的新 Tester 子 Agent，并由它在测试环境独立确认需求目标达到。
- 自动化测试或固定静态检查矩阵只在用户明确要求时执行。
- 迁移、配置、兼容或回滚限制已在需要时记录。
- 没有泄露 Secret，也没有把核心目标的明确失败或 `blocked` 标记为通过。

纯文档或不影响运行时的维护变更无需部署 Plane，但仍应验证链接、格式或对应的静态结果。
