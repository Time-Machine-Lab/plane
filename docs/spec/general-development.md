# 通用开发规范

## 适用范围与优先级

本规范适用于整个仓库。执行任务时按以下顺序读取约束：用户明确要求、根目录及最近目录的
`AGENTS.md`、OpenSpec change 产物、本目录规范、目标模块的既有代码模式。发现冲突时必须在
实施前说明冲突和采用的依据。

## 基础工具链

- Node.js：`>=22.18.0`。
- 包管理器：根 `package.json` 锁定的 pnpm `11.3.0`，禁止使用 npm 或 Yarn 改写 lockfile。
- Monorepo：Turborepo；优先使用 `pnpm turbo run <command> --filter=<package>`。
- Python：以 API Dockerfile 和 CI 使用的 Python 3.12 为基线。
- 前端格式化和 Lint：oxfmt、OxLint。
- Python 格式化和 Lint：Ruff，行宽 120，双引号，4 空格缩进。

## 依赖与导入

- 内部 package 依赖在 `package.json` 中使用 `workspace:*`。
- 外部依赖使用根 `pnpm-workspace.yaml` 的 `catalog:`；统一升级，不在单个包中漂移版本。
- 不同时引入多个实现相同职责的库；新增依赖需要说明现有能力为何不足。
- 应用可以依赖共享包；共享包不得依赖 `apps/*`。
- 类型导入使用 `import type`，避免循环依赖和跨包 deep import。
- 修改依赖时必须提交对应 lockfile，并检查 license、已知漏洞和构建体积影响。

## 代码与架构

- TypeScript 必须完整类型化，禁止用 `any`、非空断言或类型强转掩盖契约问题。
- 命名使用 camelCase 变量/函数和 PascalCase 组件/类型。
- 优先扩展现有模块和模式；只有在确实跨三个以上调用点复用时才增加新抽象。
- 错误必须保留上下文，使用项目 logger；生产代码不使用裸 `console.log`。
- 外部输入在边界处验证，内部逻辑使用已经验证的类型。
- 权限校验必须在服务端执行；前端隐藏按钮不构成授权控制。
- 不把 token、密码、Cookie、用户内容或个人信息写入日志。

## 变更流程

1. 在 OpenSpec proposal 中定义问题、目标、非目标、受影响模块和适用规范。
2. 跨模块、数据模型、API、权限或部署变更必须有 design。
3. tasks 按模块和可独立验证的步骤拆分，避免一个任务同时横跨大量无关目录。
4. 实施时保持改动聚焦，不混入无关重构或全库格式化。
5. 每个功能和 bug 修复必须增加与风险相称的测试。
6. 更新对用户、开发者或运维行为有影响的文档。
7. PR 填写测试场景、兼容性、迁移和回滚信息。

## 兼容与上游维护

- 团队定制尽量放在配置、extended 扩展点或独立领域模块中，减少修改上游核心代码。
- 不重写已经共享的上游历史；上游同步通过独立 PR 完成并记录 upstream SHA。
- 公共 API、事件、环境变量和数据库 schema 的破坏性变化必须提供迁移或废弃周期。
- 保留 Plane 的版权和 SPDX 声明。网络提供修改版服务时遵守 AGPL-3.0-only 的源码提供要求。

## 完成定义

任务只有同时满足以下条件才算完成：

- 实现符合 OpenSpec 验收场景和对应模块规范。
- 格式、Lint、类型、构建及相关测试通过。
- 没有新增 warning、失效链接、未处理 TODO 或敏感信息。
- 数据迁移、配置变化、发布步骤和回滚方式已记录。
- OpenSpec `tasks.md` 在验证完成后才勾选对应任务。
